# MTZ_MSQ
main_server_queue — потребитель очереди `calculation_tasks` (RabbitMQ):
скачивает входные данные из S3, выполняет расчёт AP3DMT, конвертирует
результаты в VTR и загружает `all_models.zip` обратно в S3, публикуя
прогресс в `status.json`.

## ⚠️ Требуемая настройка RabbitMQ: consumer_timeout

Расчёт AP3DMT идёт **часами**, а сообщение всё это время находится
в неподтверждённом (unacked) состоянии. Начиная с RabbitMQ 3.8.15 брокер
по умолчанию закрывает канал через **30 минут** ожидания ack
(`consumer_timeout = 1800000`), сообщение возвращается в очередь —
и задача начинает считаться заново.

На брокере (10.42.0.65) необходимо поднять лимит, например до 24 часов:

**Вариант 1 — rabbitmq.conf (все очереди, нужен перезапуск брокера):**
```ini
consumer_timeout = 86400000
```

**Вариант 2 — policy (RabbitMQ 3.12+, без перезапуска):**
```bash
rabbitmqctl set_policy long-tasks "^calculation_tasks$" \
  '{"consumer-timeout": 86400000}' --apply-to queues
```

Без этой настройки потребитель всё равно выживет (см. ниже), но каждая
долгая задача будет сопровождаться закрытием канала, повторной доставкой
и ожиданием вместо полезной работы.

## Надёжность потребителя (реализовано в consumer.go)

- **Автопереподключение**: обрыв соединения с RabbitMQ больше не убивает
  потребителя — супервизор в `main()` переподключается с экспоненциальной
  паузой (5→60 с) и перерегистрирует consumer.
- **Идемпотентность ([DEDUPE])**: перед началом обработки потребитель читает
  `status.json`. Если задача с тем же `task_id` уже `completed` и результат
  лежит в S3 — сообщение подтверждается без пересчёта. Если статус `running`
  с обновляющимся пульсом (`updated_at` свежее 5 минут) — задачу считает
  другой воркер, и потребитель ждёт его финала вместо запуска дубля.
- **Восстановление потерянного финала**: если воркер умер (или статус не
  опубликовался из-за 409) ПОСЛЕ загрузки результата — потребитель находит
  `all_models.zip` с LastModified новее отправки задачи, дописывает
  `completed` в `status.json` и подтверждает сообщение. Многочасовой
  пересчёт уже решённой задачи не запускается.
- **Публикация статуса с повторами**: 409 OperationAborted от S3 (конфликт
  незавершённого PUT того же ключа) пережидается ретраями. Терминальные
  статусы `completed`/`failed` повторяются настойчиво (~4 минуты) —
  пользователь должен увидеть результат даже при нестабильном S3.
- **Пульс (heartbeat)**: `status.json` перезаписывается каждые 30 с во время
  расчёта; основной сервер по устареванию `updated_at` отличает живой расчёт
  от мёртвого.
- Сообщения публикуются основным сервером с `DeliveryMode: Persistent`,
  поэтому переживают перезапуск брокера (очередь durable).
